あなたはこのプロジェクト(CLAUDE.md参照)の開発フロー、ステップ2「実装+テスト+セキュリティチェック」を実行する。
このコマンドは旧フローの `/implement` と `/test` を統合し、さらに決定論的な静的解析による
セキュリティチェックを組み込んだもの。テストは実装の後付けではなく、機能単位でTDD(Red→Green)を
回しながら進める。

引数: $ARGUMENTS (タスクID)

## 手順

1. `tasks/<id>-*.md` を読む。ステータスが「承認済み」でなければ処理を止め、先に `/dev-plan` での承認が必要なことを伝える。
2. `git status` で作業ツリーがクリーンであることを確認する(汚れていればユーザーに確認する)。
3. `feature/<id>-<slug>` ブランチを `master` から作成しチェックアウトする。
4. `## 実装方針` に書かれた内容を、検証可能な単位(機能・分岐条件ごと)に分解する。
5. 各単位について、次のTDDサイクルを回す:
   a. その単位の期待動作を検証するテストを `tests/` に先に書く。
   b. `PYTHONPATH=./vendor python3 -m pytest tests/ -q` を実行し、**そのテストが失敗すること(Red)を確認する**。既存機能の変更で意図せず既存テストまで壊れていないかも確認する。
   c. テストを通す最小限の実装を書く。
   d. 再度テストを実行し、**Greenになることを確認する**(Green)。
   e. 次の単位に進む。
6. `## 実装方針` に書かれた内容**のみ**を実装する。`## スコープ外` に書かれたことはやらない。範囲を広げたくなった場合はユーザーに確認する。
7. 実装中に方針とズレが生じた場合(想定より大きな変更が必要と判明した等)は、一旦止めてユーザーに相談する。黙って計画を逸脱しない。
8. 全単位が完了したら、最終確認として全体を実行する: `PYTHONPATH=./vendor python3 -m pytest tests/ -q`。失敗があれば直してGreenにする。
9. **セキュリティチェック(決定論的ツール)**: `PYTHONPATH=./vendor python3 -m bandit -r . -x ./vendor,./tests -ll -ii -f txt` を実行する。
   - `bandit` が未インストールなら `pip3 install --no-cache-dir --target=./vendor bandit` で導入してから実行する。
   - Medium以上の重要度・確信度の指摘は、テストの失敗と同様に必ず対応する: 実装を修正するか、意図的に許容する場合のみ該当行に `# nosec <ID> -- 理由` を付けて明示する(理由なしの抑制はしない)。
   - 対応後、`No issues identified.` になるまで繰り返す。
10. 意味のある単位でコミットする(テストと実装を近い単位でまとめてよい)。
11. タスクファイルに以下を記録する:
    - `## 実装メモ` — 変更したファイル一覧と実装上の判断
    - `## テスト結果` — 追加したテストの一覧・実行コマンド・最終結果(件数)
    - `## セキュリティチェック` — 実行コマンド・検出件数・対応内容(`# nosec` で許容した場合はその理由も記載)
    ステータスを「テスト合格」に更新し、`tasks/INDEX.md` のブランチ欄も更新する。
12. 次のステップ `/dev-review <id>` を案内する。

## 注意

- このサンドボックス内でFlask開発サーバーを起動しても、ユーザーのブラウザや `curl` からは到達できない(ネットワーク隔離のため)。動作確認が必要な場合はユーザー自身の端末で起動してもらう。
- Red(失敗確認)を省略しない。先に実装してから帳尻合わせのテストを書くのは、このコマンドが意図するTDDではない。
- セキュリティチェックはLLMの判断ではなく `bandit` の決定論的な出力のみで合否を決める。`# nosec` での抑制は必ず理由を添え、無条件の抑制はレビューで指摘対象にする。
